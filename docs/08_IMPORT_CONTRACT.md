# Vocation – Research Import Contracts

**Status:** Research Bundle 1.0, Research Update Bundle 2.0 and Availability Check Bundle 1.0 are implemented and versioned separately.

## 1. Purpose and contract boundaries

External Research never writes the Vocation domain model directly. It returns a versioned closed JSON contract that is parsed, schema-validated, semantically validated, translated and applied through Vocation-owned rules.

Current external input contracts:

- `schemas/research-bundle-v1.schema.json` – **Research Bundle 1.0**, initial research only;
- `schemas/research-update-bundle-v2.schema.json` – **Research Update Bundle 2.0**, controlled scoped updates;
- `schemas/availability-check-bundle-v1.schema.json` – **Availability Check Bundle 1.0**, availability evidence for known Postings.

The contracts are independent of Vocation database tables. Unknown properties in closed contract objects are blockers rather than automatic new domain fields.

Personal Vocation state is not owned by these contracts.

## 2. Research Bundle 1.0 – Initial Research

Research Bundle 1.0 remains frozen for `initial_market_research`.

Representative top-level shape:

```json
{
  "bundle_version": "1.0",
  "bundle_id": "research-run-001",
  "generated_at": "2026-08-06T17:00:00Z",
  "research_scope": {
    "type": "initial_market_research",
    "as_of_date": "2026-08-06",
    "search_profile": "Junior software roles",
    "constraints": ["Hamburg or remote"]
  },
  "sources": [],
  "source_references": [],
  "companies": [],
  "opportunities": [],
  "postings": [],
  "observations": [],
  "assessments": [],
  "warnings": []
}
```

The schema remains the authority for exact required/optional fields.

### Profile-aware prompting without contract mutation

Post-v0.4 Initial Research uses a Vocation-owned Prompt Context Snapshot containing the exact Search Profile revision and, when explicitly included, Candidate Profile revision.

This does **not** add profile IDs or `prompt_context_ref` to Research Bundle 1.0.

The normal inline workflow can separately send the Vocation-issued opaque Initial Research `prompt_context_ref` to the internal import API. When present:

1. it must resolve to an Initial Research Prompt Context Snapshot;
2. the returned bundle `research_scope` must exactly match the snapshot's canonical expected scope;
3. an accepted import persists the prompt-context linkage as Vocation provenance.

Legacy/manual 1.0 imports without a context reference remain valid and persist null prompt provenance.

## 3. Bundle-local IDs and Vocation identity

- bundle `id` values are nonempty, unique within their collection and local to that bundle;
- internal Vocation IDs are generated by Vocation and do not appear as Research Bundle IDs;
- references must resolve to the expected bundle collection;
- imported data cannot supply Personal Assessments, Decisions, Tracking Status, notes, Groups/Waves, Candidate/Search Profiles or Application state.

## 4. Sources and source references

A Source describes the information origin, e.g. a company careers site or job board. A Source Reference is a concrete evidence reference.

Source references carry the contract-defined Source relation, absolute HTTPS URL and observation/provenance data.

Import does not open URLs. URL structural acceptance is not proof that a posting is still available; current actionability is represented separately through Availability evidence.

Real-market prompts should prefer official company/original posting references where available, but the import contract itself validates structure/provenance rather than performing live crawling.

## 5. Companies, Opportunities and Work Locations

Imported Companies/Opportunities carry bundle-local identity/evidence and source provenance according to the schema.

Work Locations are external job evidence with explicit Precision. They are not map coordinates and are not Search Profile Search Areas.

Vocation map resolution/geocoding remains supporting local state outside Research Bundle identity semantics.

## 6. Posting identity

Safe deterministic Posting identity:

1. Source + `external_posting_id` when available;
2. otherwise normalized canonical HTTPS URL from the relevant Source Reference.

Rules:

- similar title/company/location text alone never authorizes automatic identity merge;
- contradictions between supplied identity evidence and known deterministic identity are blockers;
- uncertain similarity may produce/reuse a Duplicate Case but never a destructive merge.

## 7. Observations

Research Observations are typed, sourced and time-bound.

Research Bundle 1.0 supports the schema-defined observation types, including the implemented job-analysis dimensions such as technology requirement, task, seniority, experience requirement, work model and salary.

An Observation is evidence, not the canonical truth and not a personal Decision.

## 8. External Assessments

External Assessments originate from external research and reference known Vocation-owned Assessment Criteria.

Import requires:

- known active Criterion;
- supported subject type;
- value valid for Criterion type/range/categories;
- required source references/provenance.

External Research cannot define arbitrary new Criterion semantics inside a bundle and cannot overwrite Personal Assessments.

## 9. Structural and semantic validation

Before any domain mutation, Vocation checks at least:

- JSON syntax;
- supported bundle version and correct schema dispatch;
- JSON Schema including formats/closed objects;
- unique local IDs and valid references;
- allowed subject/observation types;
- known Criteria and valid values;
- absolute HTTPS source references where required;
- valid date/time fields;
- Company/Opportunity/Posting relationship consistency;
- deterministic Posting identity;
- prompt-context/scope/correlation requirements for the selected workflow;
- absence of protected/private fields.

All blockers are detected before the accepted domain apply transaction.

## 10. Atomic import

Accepted Research/Update imports are applied atomically:

- any blocker prevents all business mutations;
- warnings do not by themselves block;
- rejected-attempt reporting/audit may be persisted separately;
- no silent partial domain import is allowed.

## 11. Fingerprint and idempotency

Import fingerprint uses the implemented canonical JSON/SHA-256 rules. Whitespace/object-key order do not create a second logically identical import; array order remains significant where the canonicalization rules preserve it.

A previously successfully applied fingerprint is not applied again.

## 12. Research Update Bundle 2.0

Research Bundle 1.0 remains initial-only. Controlled updates use `schemas/research-update-bundle-v2.schema.json`.

Update Bundle 2.0 requires its contract-defined `prompt_context_ref` and one of the supported scopes:

- `full_update`;
- `company_update`;
- `opportunity_update`;
- `gap_filling`.

### Correlation references

Vocation creates opaque Correlation References inside one Prompt Context Snapshot.

They:

- are snapshot-local;
- may change between Prompt Runs;
- reveal no internal ID structure;
- resolve exactly one known Company/Opportunity/Posting subject;
- can be echoed by Research but never invented;
- do not permit arbitrary re-parenting/ownership changes.

Bundle-local IDs remain the references inside the returned JSON structure.

### Scope rules

- Full Update may introduce new supported subjects according to the 2.0 schema/rules.
- Company Update is constrained to selected known Companies and permitted descendants; it does not introduce unrelated Companies.
- Opportunity Update is constrained to selected Opportunities and permitted Posting descendants.
- Gap Filling may only return the explicitly requested permitted missing/evaluation evidence and does not create unrelated subjects/duplicates.

Scope violation is rejected before mutation.

### Update identity/evidence

Posting identity remains the same deterministic Source/external-ID or normalized HTTPS-URL rule. If Correlation Reference and independent identity evidence contradict each other, the update is rejected as an identity conflict.

`possible_duplicates` is only possible-identity evidence. It never confirms/merges Subjects and cannot carry personal Duplicate Decisions.

### Protected state

Research Update 2.0 never owns/mutates:

- Candidate/Search Profiles;
- Personal Assessments;
- Tracking Status;
- Decisions/Exclusion/Restore;
- private Opportunity notes;
- Groups/Application Waves;
- ApplicationCases/Materials/Documents;
- Availability observations unless using the dedicated Availability contract.

## 13. Availability Check Bundle 1.0

Availability Check Bundle 1.0 is a separate contract for known Postings.

Its observations are append-only. Supported outcomes map conservatively into derived Availability:

- explicit available → available evidence;
- explicit unavailable → unavailable evidence;
- temporarily unreachable / not found / indeterminate → uncertain evidence.

A missing page or stale search hit is not deleted from history. Negative current evidence changes the derived actionability while original Research provenance remains.

## 14. Traceability

Current traceability rules:

- Initial 1.0 manual/context-free import: no prompt-context provenance;
- Initial 1.0 linked profile-aware import: separate internal Initial Research prompt-context reference may be validated/persisted;
- Update 2.0 import: contract requires the valid update `prompt_context_ref`;
- import records preserve bundle version/fingerprint/result/provenance;
- external contracts do not expose internal Candidate/Search Profile IDs.

`ResearchImport` provenance references Prompt Context, not a requirement to expose internal Prompt Run IDs to external bundles.

## 15. Error categories

Stable implementation uses structured errors for categories such as:

- invalid JSON / unsupported version / schema failure;
- unknown/bad references;
- invalid date/URL;
- unknown Criterion/invalid assessment value/subject mismatch;
- protected field attempt;
- unknown/mismatched Prompt Context;
- scope violation;
- identity conflict;
- invalid duplicate evidence;
- already applied import.

Exact API/internal error codes remain defined by implementation/tests and must stay synchronized with contract tests.

## 16. Examples and tests

Representative repository fixtures include:

- initial-import examples under `examples/imports/`;
- update examples under `examples/updates/`;

Schema/contract tests validate frozen contracts independently from the live web.

## 17. Post-v0.4 research strategy does not silently alter contracts

#49 plans company-first, role-first, domain/technology, regional, freshness and gap/coverage Research Strategies.

A Research Strategy describes **how/where the external research is performed and what coverage is tracked**. It does not automatically require a new bundle version.

If a future strategy genuinely needs new external payload semantics, that change requires a separately reviewed versioned contract rather than adding fields silently to Research Bundle 1.0 or Update Bundle 2.0.
